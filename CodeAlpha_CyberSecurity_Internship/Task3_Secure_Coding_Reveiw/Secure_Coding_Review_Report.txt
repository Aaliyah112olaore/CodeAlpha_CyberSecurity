            CODEALPHA SECURE CODING REVIEW

Application: Python login and Registration System
Programming Language: Python 

FINDING 1: Plain-Text Password Storage

Risk Level: High

Problem:
The Application stores passwords directly without protection.

Risk:
If the stored data is accessed by an unauthorized person,the password could be read.

Recommendation:
Passwords should be securely hashed before being stored.


FINDING 2: Lack of Input Validation

Risk Level: Medium

Problem:
The application accepts any username and password without checking whether the input is valid or meets basic
requirements.

Risk:
Invalid or unexpected input can cause problems for the application and may create security weaknesses.

Recommendation:
Validate user input and apply reasonable requirements before accepting usernames and passwords.


FINDING 3: No Protection Against Repeated Login Attempts

Risk Level: Medium

Problem:
The application does not limit the number of failed login attempts. This could allow repeated password-guessing attempts.

Risk:
An attacker could repeatedly guess passwords without the application slowing down or temporarily blocking further
attempts. 

Recommendation:
Implement a limit on failed login attempts and temporary block further login attempts and temporary block further login attempts after several
unsuccessful tries.


FINDING 4: Weak passwords Requirements

Risk Level: Medium

Problem:
The application accepts any passwords without checking its length or strength.

Risk:
Users may choose passwords that are easy to guess, which can make their accounts easier to compromise.

Recommendation:
Require passwords to meet reasonable security requirements, such as a minimun length, and encourage users to use strong,
unique passwords.


Finding 5: Username Enumeration

Risk Level: Low

Problem:
The application may reveal whether a username exists by giving different responses during login or registration.

Risk:
An attacker could use this information to identify valid usernames.

Recommendation:
Use general error messages that do not reveal whether a username exists. Apply constitent responses for unsuccessful
login attempts.


Finding 6: Unsalted Password Hashing

Risk Level: Medium

Problem:
The "secure" version hashes passwords using SHA-256, but does not add a salt before hashing. This means two users who choose the same password
will end up with the exact same stored hash.

Risk:
If the stored data were ever leaked, an attacker could spot which users share the same password by comparing hashes, or use a precomputed table 
of common password hashes to crack them faster than if each password had been salted individually.

Recommendation:
Use a salted password hashing method such as PBKDF2(hashlib.pbkdf2_hmac) or bcrypt, generating a unique random salt for each user and storing it
alongside the hash.



Finding 7: Login Flow Logic Errors

Risk Level: Low

Problem:
While testing the secure version, two logic errors were found in the login function:
1. Entering a wrong password caused the password to exit the login function completely instead of asking again.
2. After successfully logging out, the program looped back and asked for a username again instead of ending the session.

Risk:
While not a direct security vulnerability, these errors created unpredictable program behaviour and a poor user experience, which can mask other
bugs and make the authentication flow harder to trust or test reliably.

Recommendation:
Use "continue" or retry a loop instead  of "return" exiting the whole function, and ensure a "break" statement is used to properly exit loops 
once their condition(correct password, successful logout) has been met.


REMEDIATION PLAN
1. Password Security
Replace plain-text password storage with secure password hashing.

2. Input Validation
Validate username and passwords before accepting them.

3. Login Protection
Limit repeated failed login attempts to reduce password-guessing risks.

4. Password Requirements
Require passwwords to meet a reasonable minimum length.

5. Username Protection 
Use consistent error messages so the application does not reveal whether a username exists.

6. Unsalted Password Hashing
Add a unique random salt per user before hashing passwords, instead of hashing with no salt.

7. Login Flow Logic Errors
Fix loop control in the login function so wrong passwords retry instead of exiting, and successful logout properly ends the session instead of 
looping back to the username prompt.

       SECURE CODING RECOMMENDATIONS
- Never store passwords in plain text.
- Validate user input.
- Protect authentication functions against repeated failed attempts.
- Use clear and consistent error messages.
- Review and test code regularly for security weakness.
- Always add a unique random salt before hashing passwords.
- Ensure loops use "continue" and "break" correctly so login and logout behave predictably.

CONCLUSION

The original application contains several security weaknesses, including plain-text password storage, weak password requirements, insufficient
protection around authentication and username enumeration through inconsistent error messages butfurther reveiw found that it still hashes
passwords without a salt, and contained two logic errors in the login flow that caused unpredictable behaviour for users.

The application can be improved by applying secure coding practices, validating input, protecting passwords with salted hasing, strengthening
the login process.
